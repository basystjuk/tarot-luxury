# ADR — Architecture Decision Records
`v1.0 · 2026-07-06` · формат: Проблема · Варіанти · Рішення · Чому · Наслідки

> ADR-001…005 — ретроспективна фіксація рішень до-OS періоду (щоб «чому так?» мало відповідь).

## ADR-001 — Next.js на Vercel
**Рішення:** Next.js (App Router) + Vercel. **Чому:** SSR/RSC + i18n + безкоштовні preview-деплої + crons без сервера. **Наслідки:** serverless-ліміти (таймаути), прив'язка до платформи.

## ADR-002 — Supabase як БД/auth
**Рішення:** Supabase (Postgres + auth + RLS). **Чому:** безкоштовний старт, RLS = безпека на рівні БД, SQL-міграції в git. **Наслідки:** ⚠ бекапи залежать від плану (BACKLOG S2); vendor lock мʼякий (Postgres — переносний).

## ADR-003 — Groq для AI-інструментів
**Рішення:** Groq API (усі тули). **Чому:** швидкість/ціна. **Наслідки:** єдина точка відмови всіх тулів → обовʼязковий fallback (TOOLS_AI); зміна провайдера = зміна одного шару (lib/ai-prompts + роути).

## ADR-004 — PostHog (EU) для аналітики
**Рішення:** PostHog Cloud EU, proxy /ingest. **Чому:** продукт-аналітика (retention/воронки), GDPR-EU, обхід блокувальників. **Наслідки:** публічний ключ у бандлі (за дизайном); PII в події не класти.

## ADR-005 — Vercel Blob для адмін-оверрайдів
**Рішення:** контент/промпти/галерея адмінки — у Blob. **Чому:** без окремої CMS; редагування без деплою. **Наслідки:** контент поза git → важливе дублювати (експорт при нагоді).

## ADR-006 — Telegram як канал утримання (не email)
**Рішення:** звʼязка кабінет↔бот↔канал @ellen_rouge; нотифікації TG+web-push. **Чому:** аудиторія живе в TG; вища відкриваність за email. **Наслідки:** залежність від платформи TG; токен = критичний секрет (SECURITY, W5).

## ADR-008 — Адмінка 2.0: розділи з адресами, одна модель збереження, версії `🟡 PROPOSED — реалізовано на етапі 1 (2026-10-08), чекає підтвердження власника`
**Проблема:** адмінка була одним файлом на 2300 рядків: 15 вкладок в один рядок (не вміщались навіть на 1280px, на телефоні — непридатна), невидимі заголовки, три різні способи зберігати (автозбереження на кожен символ / кнопки / суміш), кожне збереження перезаписувало весь `site-content.json` без копій і без захисту від одночасних змін.

**Рішення:**
- **Структура:** `app/admin/layout.tsx` + сторінка на кожен розділ (`/admin/services`, `/admin/faq`, …) — адреси працюють, «назад» і оновлення сторінки не гублять розділ. Бічне меню з групами (Огляд · Контент · Медіа · Інструменти · Аудиторія · Сайт · «Не відображається на сайті»); на телефоні — меню-шухляда.
- **Одна модель збереження:** увесь контент редагується в спільному стані (`components/admin/content-context.tsx`); зміни локальні до «Зберегти» (панель знизу / Ctrl+⌘S); попередження при виході. Перевірка контенту (`lib/content-validation.ts`): помилки блокують збереження, зауваження — ні.
- **Сховище:** `lib/content-store.ts` — запис з версією (ETag, `ifMatch`) → чужа зміна дає 409, а не перезапис; копія попередньої версії раз на ≤10 хв (30 останніх), відновлення з UI («Історія версій»); локальне файлове сховище для тестів (`admin-safe-local`).
- **Вигляд:** світла кремова тема на токенах палітри (як сайт), набір компонентів `components/admin/ui.tsx` (Radix + CVA, без нових бібліотек), цілі ≥44px, поля 16px на мобільному.
- **Чесність інтерфейсу:** розділи, які сайт зараз не показує (відгуки, hero головної, блог-блок, фото профілю), позначені «Не відображається на сайті»; дані не видалено.

**Альтернативи:** готова headless-CMS (Sanity/Strapi) — відхилено: нова залежність і міграція даних заради функцій, які покриває власний шар; перенос контенту в Supabase-таблиці — відкладено до потреби в записах із пошуком/фільтрами (зараз один документ <30 КБ).

**Наслідки:** доступ до адмінки поки той самий (спільний пароль) — заміна на персональні акаунти з ролями = окрема критична фаза (етап 3); від неї залежать журнал дій і «хто змінив». Стиль змінюється заміною токенів, не версткою.
