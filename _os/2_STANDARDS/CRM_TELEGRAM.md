# CRM_TELEGRAM — база клієнтів + Telegram (пріоритет №4, актив бренду)
`v1.0 · 2026-07-06 · owner: Claude(CTO)`

## Архітектура звʼязки (факт)
Кабінет ↔ бот: link-token (`t.me/<bot>?start=<token>`) → webhook (`TELEGRAM_WEBHOOK_SECRET` перевіряється) → запис telegram_id у профіль. Канал **@ellen_rouge** — бот адмін (getChatMember = перевірка підписки). Нотифікації: Vercel cron 04:00 → TG/push за prefs користувача. Send log — кожна відправка.

## Секрети (урок GrandKeram E4 — токен у клієнтському коді = вкрадений токен)
- `TELEGRAM_BOT_TOKEN`, `SUPABASE_SERVICE_ROLE_KEY`, `CRON_SECRET`, `TELEGRAM_WEBHOOK_SECRET` — **тільки server-side** (env). Жодного `NEXT_PUBLIC_` для секретів. Перевірка при рев'ю: `grep -r "TELEGRAM_BOT_TOKEN" app components` не має влучати в client-компоненти.
- Компрометація токена = пожежний виняток: відкликати в BotFather ОДРАЗУ, потім розбір.

## Розсилки — правила (репутація каналу дорожча за буст)
1. **Масова відправка — лише за явним «так» власника** на конкретні: текст (3 мови? чи мова сегмента) + аудиторія + час.
2. Спершу **тест на себе/тест-акаунт**, потім масово.
3. Кожна відправка → send log (хто/що/коли/скільком). Помилки доставки — рахувати, не ковтати.
4. **Opt-out священний:** prefs користувача перевіряються перед КОЖНОЮ відправкою; відписався = не отримує.
5. Частота: ⚠ визначити з власником ліміт (гіпотеза: ≤2-3 пуш-повідомлення/тиждень на людину, дайджест краще за спам).

## База клієнтів
- Джерело правди — Supabase (profiles + telegram + prefs). Адмінка (`/admin/users`) — перегляд/повідомлення.
- Сегменти: за мовою, підпискою на канал, активністю в тулах (PostHog-звʼязка). Персональні повідомлення з адмінки — теж у send log.
- Експорт клієнтів (CSV тощо) — лише за запитом власника, файл поза git, після передачі — видалити локально.

## Ріст бази (напрям)
Кожен інструмент має мʼякий місток: результат → «збережи в кабінеті» → «отримуй персональні підказки в TG». Не примус: цінність спершу, підписка потім.
