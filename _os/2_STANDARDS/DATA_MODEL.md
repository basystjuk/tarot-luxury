# DATA_MODEL — база даних (Supabase)
`v1.0 · 2026-07-06 · owner: Claude(CTO)` · клієнтська база = головний актив

## Канон схеми
**Схема = сума нумерованих міграцій** `supabase/migrations/000N_name.sql`. Будь-яка зміна БД — НОВА міграція (не редагувати старі, не «клікати» в Supabase Studio без файлу). Поточні: 0001 profiles+tarot_history · 0002 telegram (link-tokens/prefs/send log) · 0003 push · 0004 notifications · 0005 youtube_videos.

## RLS — ЗАЛІЗНЕ правило
- **Кожна нова таблиця = RLS enabled + політики в тій самій міграції.** Таблиця без політик у прод не їде (аналог GrandKeram: «відкрита база = витік»; там це коштувало інциденту E1).
- Патерн для користувацьких даних: `auth.uid() = user_id` на select/insert/update/delete (еталон — 0001_profiles.sql).
- Службові таблиці (send log, youtube) — читання лише service role / admin.
- **Прод-перевірка після деплою:** спроба читання чужого запису анонімом → має бути denied.

## PII (мінімізація)
- Зберігаємо лише потрібне для функції: імʼя/мова/дата народження (для тулів)/telegram_id/пуш-підписки/історії тулів.
- ❌ Не логувати PII в консоль/аналітику/error-трекінг. ❌ Не віддавати в клієнтський бандл нічого, крім власних даних користувача через RLS.
- Видалення акаунта → каскад (`on delete cascade` — еталон у 0001).

## Бекапи (урок GrandKeram №8)
⚠ **ПЕРЕВІРИТИ:** чи включені бекапи в плані Supabase (free tier = обмежені!). Якщо ні — щоденний експорт критичних таблиць (profiles, telegram, prefs) скриптом у приватне сховище. Задача в BACKLOG до зʼясування. Бекапи з PII — ніколи в git.
